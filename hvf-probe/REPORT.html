SPTM Under Hypervisor.framework

Apple's hypervisor now offers guests a real EL2, and QEMU already knows how to use it. It still cannot run an SPTM kernel, and the reason is structural rather than a missing patch.

The finding

Traps are the currency, and EL2 does not pay

Trap-and-emulate only works when the hypervisor sees the access. On this Mac, a guest running at EL1 in an ordinary virtual machine hands the VMM every Apple implementation-defined register access as a clean system-register trap, complete with the register encoding and the destination register. That is exactly the raw material a darwin machine would need.

Raise the guest to EL2, which is where SPTM lives, and that channel closes. The same instructions become undefined instructions taken by the guest itself. The VMM is never told. There is no control that redirects them, because the exception is already being delivered at the highest exception level the guest has.

Toolchain

The fork already has the EL2 backend

The qemu-sptm tree is QEMU 11.1.0, and 11.1 is the release that landed HVF nested virtualization. Every piece is present: the support check, the configuration call that enables guest EL2, the full table of EL2 system registers, and a PSCI path that starts secondary cores at EL2. No patch series needs porting and no mailing-list archaeology is required.

What is missing is one wire. The switch that turns the feature on is called from exactly one place in the tree, the virt machine's virtualization property. The darwin machine does not mention the accelerator anywhere.

Probe

What each feature actually does

A standalone program builds a virtual machine, maps two megabytes of guest memory, writes hand-assembled instructions into it, and runs them. Each probed register or instruction sits in its own forked child with its own virtual machine, so a fatal outcome costs one line of the matrix rather than the run. Results come back through an unmapped address that turns every store into an exit the harness decodes.

Four configurations were swept. The classification is: native the instruction ran and returned a value, to VMM the hypervisor was handed the access, guest UNDEF the guest took an undefined-instruction exception the VMM never saw, and abort Hypervisor.framework killed the process.

The exception syndromes are complete

Where an access does trap out, the information is everything an emulator needs. A read of the SPRR configuration register from EL1 arrives as syndrome 0x6231bc03, which decodes to the exact encoding, the direction, and the destination register. Writes carry the source register the same way. There is no guesswork and no instruction refetch.

Guarded execution cannot be emulated at all

Every Apple register can at least be intercepted somewhere. The genter instruction cannot. In an ordinary virtual machine the guest at EL1 executes it and takes its own undefined-instruction exception. The VMM is not involved, so there is no opportunity to synthesise the guarded-mode entry that the fork implements in software. Redirecting undefined instructions to the host would need a control the framework does not expose, and setting it would break the guest kernel in other ways.

This matters because guarded execution is not incidental to SPTM. It is how the monitor separates itself from the kernel.

Memory tagging is absent and cannot be faked

The tagging feature field reads zero in every configuration even though the host silicon implements three generations of it. The tagging instructions do decode and execute, but they perform no tag work. Address arithmetic happens and the tag field stays zero, so a store-then-load round trip returns an untagged pointer.

Overriding the identification register to advertise tagging succeeds as an API call and the guest does read the new value. Nothing changes underneath. The tag control register still traps out and the instructions stay inert. Since the darwin machine already checks whether a kernel collection uses tagging and configures the CPU accordingly, tagged iOS kernels are out of reach on this path regardless of the SPTM question.

Framework defect worth filing

When a guest at EL1 under a guest EL2 executes any Apple implementation-defined register access and the guest hypervisor has not set the trap control, Hypervisor.framework does not return an error. It kills the calling process with a trace trap from an internal unimplemented path, printing FIXME IF: "Handle this" line 82. The crash report shows the abort inside the framework's own exception emulator, reached from its system-register exit handler.

This reproduces on 39 different registers and is independent of stage-2 translation. Any VMM offering nested virtualization can be killed by unprivileged guest code, so it is worth a Feedback Assistant report with the probe attached.

Recommendation

Neither path runs SPTM, so pick by what you actually want

Trap-and-emulate on Hypervisor.framework fails for SPTM because the registers SPTM needs are invisible at the level SPTM runs at. Adding emulation code cannot fix an access the hypervisor is never told about.

Asahi Linux with KVM does not solve it either, and it is worth being precise about why. On bare metal the Apple registers and guarded execution are real hardware, so they work. But SPTM still wants its own EL2, and giving a guest a real EL2 needs the architectural nested-virtualization extension that Apple's cores do not implement. Apple's own EL2 for guests is a software construction inside the framework, which is exactly why it has unimplemented paths that abort.

So the honest ranking depends on the goal behind the question.

  • If the goal is a fast SPTM kernel, stay on TCG. Nothing available on this machine changes that today, and the fork's emulation is the only thing that models guarded execution and the monitor's registers at all.
  • If the goal is a fast XNU, an HVF path for kernels that do not use SPTM is genuinely attractive. Those run at EL1, every Apple register access lands in the VMM with a complete syndrome, and the existing register handlers can be reused nearly as they are.
  • If the goal is bare-metal fidelity, Asahi with KVM gives real Apple registers and real guarded execution for an EL1 guest, without a software EL2. It is the better long-term host for kernel work, at the cost of a second machine and a very different bring-up.

Between the two the study asked about, prefer the HVF path, scoped to kernels without the monitor. It reuses the tree you already have and it is the only one of the three that is a bounded piece of work.

Scope

Adding an HVF path to the darwin machine

This estimate covers a non-SPTM kernel booting at EL1 under the hardware accelerator, on a branch that leaves the current TCG behaviour untouched. It does not cover SPTM, which the findings above rule out.

  • Route unknown system-register traps to the Apple table 1 day The accelerator already has a helper that looks up a register by encoding and calls its read or write function. The Apple registers are defined in that same form. The change is to consult that table in the fallback case instead of injecting an undefined instruction.
  • Machine wiring and an accelerator guard 1 day Select the CPU and reset path by accelerator, refuse the combination of the monitor and hardware acceleration with a clear message, and set initial state through the accelerator rather than by writing the emulated register file.
  • Correct the guest-visible identification registers 1 day The exception-level field reads zero and the tagging field is fixed at zero. Both need deliberate handling so the kernel's own feature probing sees something coherent.
  • Interrupt controller and timer under the accelerator 3 to 5 days The darwin machine wires the hypervisor virtual timer to fast interrupts, which suits emulation. The accelerator reports timer expiry only as its own exit and expects the VMM to inject through the guest's controller. This is the least mechanical item and the most likely to surprise.
  • Memory map, address space size, and bring-up debugging 3 to 5 days Map the Apple physical layout within the intermediate address limit, then work through whatever the kernel does differently when its register accesses are real rather than emulated.

Call it two to three weeks of focused work to a first boot attempt, with the timer path carrying most of the risk. The register plumbing itself is small because the accelerator and the Apple register definitions already speak the same interface.

Reproducing

The probe

The program is standalone C against Hypervisor.framework with no QEMU dependency. It is ad-hoc signed with the hypervisor entitlement during the build, which needs neither administrator rights nor a developer account. Every hand-encoded instruction is cross-checked against the system assembler by a separate target, so an encoding mistake cannot be misread as a hardware finding.

cd ~/Downloads/darwin-vm/hvf-probe
make          # build and sign
make check    # diff hand-encoded words against clang, prints "encodings match clang"
make run      # full sweep, writes results.txt
./summarize.py results.txt   # one line per probe, with a verdict class

Useful flags are --modes=1 to run a single configuration, --verbose to print every exit as it happens, and --try-force-mte to repeat the tagging experiment after overriding the identification register.

Files
  • hvf_probe.c harness, register table, mini assembler, and the four configurations
  • check.S the same instruction list for the assembler to encode
  • summarize.py reduces the transcript to a table
  • results.txt the full sweep behind every claim here
  • results-summary.tsv and results-tally.txt the derived tables

Nothing in the QEMU build tree or the display working tree was touched.
