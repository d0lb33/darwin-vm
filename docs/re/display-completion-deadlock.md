# D594 completion / power lock deadlock

Build: iOS 27 24A5430a, six-core TCG. Kernel addresses below are unslid;
runtime kernel slide is `0x20000000`. This is separate from SKS and surface
cache blockers. The Cocoa framebuffer held the last frame because no new
frame submissions arrived.

## Measured cycle (2026-09-05)

`NATIVE_INPUT_BOOT2/stderr.log:41403-41412` under `/tmp/dvm` ends IOMFB traffic
with A408 RPC 9824, one 1179x2556 presentation, D594 callback 46 for swap ID 0,
and A500 RPC 9825. A500 received status 0; D594 never completed. The earlier
45 completions prove that zero is a valid reused native queue identifier.
Restores R4 and R5 inherit this stall; neither produces subsequent IOMFB RPCs.

`/tmp/dvm/DISPLAY_FREEZE_R5.lock-cycle.json` records:

| Object | Address / value |
|---|---|
| BackBoard render thread | `0xffffffe33b0ed8f0` |
| Its wait event | `0xffffffe33c255d68` |
| Link-state object | `0xffffffe33c255900` |
| Incoming tag-0 slot | link + `0x408` = `0xffffffe33c255d08` |
| Slot state (+0x60) | 1 (active) |
| Slot owner (+0x38) | `0xffffffe33bce3060` |

BackBoard's userspace chain reaches `_kern_SwapEnd` at shared-cache static
`0x22a391368`. Its kernel chain reaches `a0cf7a8`: the power transition is
sleeping on the active incoming slot's +0x60. D594's kernel chain includes
`a0db148`, `a0c5a98`, `a0c500c`, `a0b9924`, `a0bb0b8`, and `a0d5b3c`.
At `a0d5b34-a0d5b38`, set_device_power locks its object's +0x80
IORecursiveLock. These two waits form a circular dependency.

Saved chains: `/tmp/dvm/DISPLAY_FREEZE_R5.{bb,d594}-kernel.json`.
SpringBoard's main thread is downstream in `CA::Render::Message::send_message`
(static `0x184404fb0`), consistent with a blocked display server.
`tools/re/display_lock_cycle.py` can reproduce the bounded pointer witness.

## Corrected ordering

The old model replies to A408, then sends D594 asynchronously with ack=1.
That lets BackBoard enter power teardown while the other kernel thread is
still releasing completed surfaces. Simply sending the asynchronous message
a little earlier does not serialize its execution.

The native protocol supports callbacks nested inside an outstanding AP RPC:

- `rpc_caller_gated` at `a0ce750-a0ce770` distinguishes a final `0x42` reply
  from an incoming callback, executes the callback on the waiting caller,
  and resumes waiting for the final reply.
- `link_state_init` at `a0cf66c-a0cf67c` assigns outgoing slot RX windows to
  heap + `0x60000 + tag*0x8000`. Its existing slot keeps ack=0 and the AP tag.
- `rpc_callee_gated` at `a0cf298-a0cf2b4` replies using that slot's tag/ack.
- The AP queue item exists before A408 (`a0c3730` -> `a0c4500`).
- The drain at `a0cf74c-a0cf754` explicitly skips slots owned by its current
  thread; IORecursiveLock also permits reentry by that thread.

Model behavior: copy the submitted surface, send D594 through the
still-pending A408's ack-0 RX slot, await the native callback return, then
reply to A408. Keep each tag's pending ID in an optional migration subsection.
Old asynchronous completion state remains readable for existing snapshots.

## Runtime validation

`DISPLAY_NESTED_R1` restored the six-core `DISPLAY_SMP6_HOME13` checkpoint,
using its existing migrated disk. It recorded **853 presentations and 853
successful nested completions**, with no outstanding callback at capture,
57 A500 calls/replies, and 5,143 each successful set_device_power off/on
returns. Zero panics and no unexpected protocol messages. Counts are in
`/tmp/dvm/DISPLAY_NESTED_R1.completions.json`, generated by
`tools/re/display_completion_report.py`. These counts demonstrate the driver
returning through the formerly blocked power path, not just QEMU running.

The native D594 entry witness uses ack-0 slot `0xffffffebe83ff468`, owned by
thread `0xffffffeb02c118f0`. The live chain goes through `a0ce770` (the
RPC caller's nested-dispatch return) and `a0c91f4`/`a0c4668` (A408/SwapEnd).
It does not dispatch this completion on a separate workloop. See
`/tmp/dvm/DISPLAY_NESTED_R1.native-{slot,chain}.json`.

The clock hand changed between `DISPLAY_NESTED_R1.first.png` and
`DISPLAY_NESTED_R1.clockC.png` (1,013 changed pixels in the clock crop).
Two 12-second running samples recorded 98 and 75 presentations, or 8.15 and
6.24 submissions/second; those are not a benchmark of unique frames or an
FPS promise. The debugger-running fractions were 100% and 99.1%.

Snapshot compatibility tests with the final binary
`4e201b275e55095e1d9215d8c5f6d9ba351b8ba4cbacf0c9b54acb77612b0740`:

## Continuing from the working state

Use `/tmp/dvm/checkpoints/DISPLAY_NESTED_INFLIGHT2/manifest.json` with
`tools/restore_checkpoint.py`. The checkpoint retains the Home13 disk
lineage and shared-cache slide **0x14f94000**, not the newer native-input
boot's 0xa09c000 slide. No data migration or cold boot is needed.
The current visible test instance is `DISPLAY_NESTED_R3` (GDB 1511, monitor
`/tmp/dvm/DISPLAY_NESTED_R3.restore.sock`). The native-input helper changes
remain in their separate image lineage; this display baseline predates them.

This fixes the measured D594/power-lock cycle. It does not complete cold
display bring-up without LLDB: the existing software-surface allocation and
boot/UI accommodations are separate work. New surface allocations can still
need `tools/input/display_callbacks.py` with the correct shared-cache slide.

At the end of this test LLDB was detached from R3, with all its breakpoints
removed. `/tmp/dvm/DISPLAY_NESTED_R3.no-lldb-perf.json` then recorded 137
presentations in 30.093 seconds (4.55 submissions/second), with all 291 QMP
samples reporting running. The visible QEMU instance remains running without
LLDB attached. This proves continued warm-state rendering without a debugger;
it does not prove a debugger-free cold boot or new-surface allocation path.
